# 性能与负载控制

## 选择请求形态

| 工作负载                     | 调用方式                             | 上游请求              |
| ---------------------------- | ------------------------------------ | --------------------- |
| 一份上下文，多项独立判断     | 单类工具的 items 或 assess_structure | 1 次，共享上下文      |
| 多份独立上下文，相同判断标准 | assess_batch 的 records              | 每记录 1 次，有界并发 |
| 前次答案决定后续内容或选项   | 调用方按依赖执行下一步               | 按依赖分阶段          |
| 实时单次判断                 | 立即调用已有工具                     | 不延迟凑批            |

TypeSafe [建议合并相同上下文中的独立问题](https://docs.typesafe.ai/primitives/score#splitting-a-complex-judgment-into-several-score-questions)：模型并行评估问题，共享上下文可减少重复输入及往返。不同记录的并发改善完成时间，不减少它们本来的模型 token；不要把无关记录混入同一上下文。

## 调度参数

| 服务器环境变量        | 默认 | 允许范围                     |
| --------------------- | ---- | ---------------------------- |
| JEVS_MAX_CONCURRENCY  | 4    | 1–64                         |
| JEVS_MAX_QUEUE        | 32   | 0–1024，0 表示拥塞时立即拒绝 |
| JEVS_QUEUE_TIMEOUT_MS | 1000 | 1–60000 毫秒                 |

推理、批量记录和模型发现共享一个进程内调度器；配置目录不发送上游请求。不同进程之间不协调额度。HTTP provider 复用连接配置和 Bun 原生 fetch，通过异步 I/O 并行请求；Clef Python 复用单个 worker，内部串行评估。

无拥塞时立即执行；队列容量只限制等待项。超过容量或期限会在发送上游前失败，错误契约见 [协议说明](protocol.md#失败与恢复)。

`assess_batch` 最多 32 条记录，通过有限工作循环逐条补位，为其他等待调用保留获得执行名额的机会。单个 batch 等全部记录结束后返回；每条评估按 `JEVS_REQUEST_TIMEOUT_MS` 超时（默认 30000ms，MCP 调度等待另计），整批没有独立的总期限。服务不自动重试；调用方按失败原因与预算决定重试，网关可能有独立策略。调用方应按宿主期限选择批次大小。

本地 Clef 的内部串行等待、加载与推理计入该评估期限；排队取消/到期只移除该请求，活动评估取消/到期终止 worker。增加 MCP 并发不会使单个 worker 并行推理。

先合并共享上下文，再根据延迟尾部、429 和本地拒绝情况调整并发。实时请求适合短队列；增加排队长度不能消除过载。这些配置不代表服务商额度或硬实时保证。

## 比较不同模型

目录中的决策模态不保证协议、质量或吞吐等价。先验证目标 provider 的能力和真实账户调用，再以相同证据、标准、调用方阈值与端到端工作流比较成本、尾延迟、重试、返工与最终接受率。保留 provider、实际 model 与可用 usage；缺失 token 用量不能视为零成本，confidence 也不能跨模型直接复用阈值。

协议 fixture 和本地 bundle 验证不能证明在线吞吐或减少主模型总工作量。
